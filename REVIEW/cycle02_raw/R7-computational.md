# R7 – Computational efficiency review (cycle 2)

**Recommendation: Major revision.** The method really is cheap, but the deployment information set is not realistic, and the reported costs are measured selectively.

## Summary
The layer is closed form, and its cost grows linearly in calibration buildings × stages × grid points. Per new building, the online state is one decayed cumulative-count vector (4000 floats, about 16 KB). That state does not grow with history length. The claim that the overhead is negligible next to LightGBM training is therefore right in substance. However, the headline figure "0.015 ms per building-day" (in the abstract and §4.6) leaves out part of the layer's own work. It is compared with a pooled-CQR number that is not like for like. It also rests on one unrepeated run, and stale cost tables in the repository contradict it. The 4000-point grid is harmless (Issue 5). The main feasibility gap is the assumption that all of day D-1 is observed before the day-D forecast is issued.

## Issues

**1. Major: Day-ahead information set is not operational, and its cost was never tested.**
- *Evidence.* §2 (packet l.69) issues the forecast "at the end of day t0+h-1". The features use the previous day's full load profile (l.81). The recency layer gives weight 1 to day h-1's scores (l.108). Day-ahead nominations and flexibility bids close before D-1 ends, typically around noon, and smart-meter data often arrives with a 1–2 day delay. The limitations section (l.375ff.) does not mention data latency.
- *Why it matters.* The first-week gain (23.8% → 13.7%) depends on the most recent day getting the largest weight.
- *Action.* State the assumption explicitly and report results under a realistic lag.
- *Experiment.* (i) Calibration-only: shift the own-score state by one stage, so that day h uses scores up to h-2. This reuses stored scores, so no retraining is needed. (ii) Ideally, also lag-1-day features. Report window and first-week under-covered shares for HSC-CQR recency, QShrink (cov), ACI and CQR.

**2. Moderate: The headline per-building-day cost leaves out part of the layer and uses an unequal baseline.**
- *Evidence.* scripts/timing_benchmark.py times only `cb.hsc_quantiles(cct, …)`. `cct = cb.cum_counts(Stq)`, the conversion of the building's scores into grid counts, runs outside the timer. It is a Python double loop (calibration.py:45-57). On synthetic scores of the same shape (253×56×24), I measured cum_counts at ≈0.018 ms per building-day. That is more than the reported 0.015 ms, so the true overhead is about 2×. §4.6 does say "once the scores are stored", but the abstract does not.
- The pooled-CQR figure (0.0005 ms) times `pooled_quantile`. That function computes 7 radii shared by every building, and the time is then divided by nt·NH. A ~30× ratio between the two numbers has no meaning.
- The script's docstring promises LightGBM inference and QShrink timings. Neither is measured: `Xn = PT["yhat"]` is never used.
- In-run LightGBM inference was 0.08–0.82 ms per building-day (T_efficiency). That is 5–50× the layer's cost, and the main text never reports it.
- *Action.* Time the whole online step (binning plus radius). Report inference cost alongside it. Drop the pooled ratio or explain it. Fix the abstract wording.
- *Experiment.* Rerun the benchmark only.

**3. Moderate: Cost figures come from one unrepeated run, and repository tables contradict them.**
- *Evidence.* timing.json covers seed 0 only: 5 wall-clock repetitions with `time.time()`, no warm-up, no spread reported. Nothing enforces the "one CPU core" claim: there is no thread limit and no CPU or hardware record.
- "56 s on four cores" is one sample. In-run LightGBM times for the same configuration ranged from 26 s to 2352 s (T_efficiency: UCI s0 2352 s, BDG2 s3 755 s), which points to contention.
- tables/MS_cost.md, still generated by manuscript_tables.py:171-188, reports "HSC update 0.293 ms/building-day" and "LightGBM 270 s", labelled "mean over 5 seeds". These refer to the K-neighbour HSC-CQR, not the recommended layer, and conflict with §4.6.
- *Action.* Report the median and IQR over ≥5 repetitions and all seeds, with CPU model and thread settings, and pin threads (threadpoolctl/OMP_NUM_THREADS=1). Delete or regenerate MS_cost/T_efficiency for the recommended method.

**4. Moderate: The "portfolio-scale" claim has no scaling evidence, and the reported memory is incomplete.**
- *Evidence.* The benchmark covers only 253 targets and about 170 calibration buildings. The 18.8 MB figure is the binned store (ncal×7×4000 float32 = 112 KB per building). Three costs are not reported:
  - Leave-one-building-out tuning holds `cc` (ncal×56×4000 int16, 448 KB per calibration building; about 4.5 GB at 10⁴ calibration buildings).
  - The evaluation batch `self_cc` (253×56×4000 int16 = 113 MB, measured).
  - Per-building state at 10⁵ buildings (about 1.6 GB float32).
- The recommended variant is stage-agnostic with a uniform prior, so deployment needs only a single 4000-vector prior. The 18.8 MB store is therefore a tuning artefact, not a deployment requirement.
- *Action.* Give the complexity and memory per component (tuning, deployment prior, per-building state). Either show a synthetic scaling run (10³–10⁵ buildings), or soften "allow portfolio-scale deployment" to a complexity argument.

**5. Minor: Grid resolution is not validated in the paper, but it is harmless.**
- *Evidence.* make_grid gives a relative spacing of 0.477–0.481% for |e| > 0.1 s and an absolute spacing of 7e-5 at 0.01 s. In my check (t₄ scores, n = 100 to 2×10⁵), rounding up raised coverage by +0.02 to +0.04 pp compared with the exact conformal quantile. This is far below the 5-point under-coverage threshold, and it applies to all methods alike.
- Two caveats: INF_RADIUS = 500·s is a finite surrogate, which drives the κ=0 interval score of 18.49 in run_info. The float32 tolerance of 1e-6 in `_first_ge` is fine at the current N, but it would bias the quantile once 1/N < 1e-6 (pools larger than 10⁶ scores).
- *Action.* Add a unit test that compares grid and exact quantiles on real scores for one seed, and report the result in one sentence in §3. Note the tolerance limit for large pools.
- *Experiment.* One-seed exact-quantile recomputation.

**6. Minor: The deployment recursion is never stated.** The manuscript gives no algorithm for the per-day update (state ← ρ·state + today's counts, then a quantile by first-index search; implicit at calibration.py:200-210).
- *Action.* Add a short algorithm box that states the per-day O(NG) cost and the state that must be stored.
